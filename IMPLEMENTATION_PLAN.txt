1. EXECUTIVE SUMMARY & SYSTEM OVERVIEW
================================================================================
MediAI is an enterprise-grade hospital emergency clinical triage and patient 
prioritization web application engineered in alignment with international 
emergency triage protocols (Emergency Severity Index [ESI] and Canadian Triage 
Acuity Scale [CTAS]).

The system eliminates intake delays through accessible front-end interfaces, 
evaluates patient physiological parameters against deterministic red-flag rules, 
computes standardized acuity priority levels (P1 Critical through P4 Low), 
and presents an attending physician workstation for review, clinical rationale 
recording, and override management.

Core Architectural Goals:
- Deliver zero-lag clinical intake via lightweight, native Vanilla HTML/CSS/JS.
- Guarantee patient safety by enforcing hard deterministic physiological rules.
- Maintain immutable audit logging with zero Protected Health Information (PHI).
- Provide two-step verification (2FA OTP) for authenticated hospital staff.
- Offer bilingual clinical accessibility in English (en-US) and Tamil (ta-IN).

2. ARCHITECTURAL SAFETY INVARIANTS & GOVERNANCE
================================================================================
The MediAI system enforces five non-negotiable architectural safety invariants:

1. DETERMINISTIC RULE SUPREMACY:
   Deterministic physiological red-flag safety rules strictly override all 
   heuristic or statistical scoring. If any Tier-1 red flag matches:
   - Risk score is locked to 100.
   - Acuity priority is forced to P1 CRITICAL.
   - Mandatory physician evaluation response window is set to 0 minutes 
     (immediate resuscitation bay allocation).

2. NEVER LOOSEN A RULE:
   Safety criteria are one-way fail-safe. Missing or null vital sign inputs 
   never suppress independent checks in other domains. When essential vitals 
   (SpO2, SBP, HR) are absent, system confidence drops to LOW with prominent 
   clinical warnings.

3. PURE FUNCTION EVALUATION ENGINE:
   The clinical safety evaluation engine is implemented with pure Java Core 
   functions: zero I/O, zero network dependencies, zero external lookups, 
   ensuring predictable, deterministic output for any physiological input set.

4. ALERT FAILURE ISOLATION:
   Any failure in downstream notification dispatch or messaging channels 
   never blocks transactional database persistence or patient queue admission.

5. FAIL-CLOSED PRINCIPLE & ZERO-PHI COMPLIANCE:
   - System exceptions fail securely and never default to an unearned LOW or 
     MODERATE acuity category.
   - Patient names are encrypted at rest using AES-256-GCM.
   - Medical Record Numbers (MRNs) use salted SHA-256 hashes.
   - Audit logs store zero plaintext patient health identifiers.
   - Administrative roles view masked records: "REDACTED (ADMIN_VIEW)".

5. DETAILED SPECIFICATION OF CORE FEATURES
================================================================================

--------------------------------------------------------------------------------
5.1 FEATURE 1: BILINGUAL VOICE INPUT FOR CLINICAL SYMPTOMS
--------------------------------------------------------------------------------
- Purpose: Reduces intake delays in high-pressure emergency wards by allowing 
  hands-free speech dictation of patient chief complaints.
- UI Location: Mounted adjacent to the chief complaint input field in intake.html 
  and profile.html via a microphone button (<button class="btn btn-outline btn-sm">).
- Implementation Architecture:
  * Leverages browser-native Web Speech API (webkitSpeechRecognition).
  * JavaScript dynamically configures language to 'en-US' or 'ta-IN' based on 
    the active bilingual toggle.
  * Real-time transcribed text streams directly into the editable complaint textarea.
  * Human-in-the-Loop Safeguard: Speech is NEVER auto-submitted. Patients and nurses 
    retain full capability to review, correct, or delete transcribed text.
  * Manual Typing Fallback: Standard keyboard input remains fully functional.
  * Error Handling: Displays non-blocking inline alerts if mic access is denied.

--------------------------------------------------------------------------------
5.2 FEATURE 2: REAL-TIME CLINICAL NOTIFICATIONS & ALERT DRAWER
--------------------------------------------------------------------------------
- Purpose: Provides immediate, role-filtered clinical notifications for critical 
  patient arrivals, resuscitation flags, and doctor override events.
- UI Location: Global top navigation bell icon (🔔) with unread pill badge, 
  opening an interactive slide-out notification drawer on any page.
- Storage: MySQL 'notifications' table via Notification.java and NotificationRepository.
- Automated Trigger Workflows:
  1. Intake Completed -> Role: ALL -> Priority: INFO
     "New Triage Assessment Recorded with [Category] priority."
  2. Tier-1 Hard Red Flag / Critical Hypoxia -> Role: DOCTOR, NURSE -> Priority: CRITICAL
     "🚨 CRITICAL Triage Alert: Immediate resuscitation bay attention required."
  3. Doctor Override Applied -> Role: ALL -> Priority: HIGH
     "👨‍⚕️ Physician Triage Override: Category updated to [Target Category]."
- Endpoints: GET /api/v1/notifications, PUT /api/v1/notifications/read-all.

--------------------------------------------------------------------------------
5.3 FEATURE 3: STAFF AUTHENTICATION, RBAC & 2-STEP OTP SECURITY
--------------------------------------------------------------------------------
- Purpose: Enterprise-grade staff authentication with two-factor OTP verification 
  protecting hospital records against unauthorized access.
- Two-Step Verification Flow (signin.html):
  1. Step 1: User submits clinical email and password. Spring Security verifies 
     credentials against BCrypt password hashes in MySQL.
  2. Step 2 Dispatch: Backend generates a cryptographically secure 6-digit random 
     passcode, hashes it with SHA-256, and stores it in 'user_otps' with a 5-minute expiry.
  3. Step 2 Challenge: The login form smoothly transitions in-place to the OTP card, 
     displaying masked email (e.g., "d***r@mediai.org"), countdown timer, and OTP input.
  4. Step 2 Validation: Submitting OTP verifies the SHA-256 hash match. Upon success, 
     OTP is invalidated, and a signed JWT bearer token is issued for subsequent requests.
- Security Defenses:
  * Zero cleartext passcode storage in database.
  * Maximum 3 failed attempts before the session token is permanently revoked.
  * Re-use of validated OTP returns HTTP 400 Bad Request.
  * 60-second cooldown rate limit prevents OTP flooding.

--------------------------------------------------------------------------------
5.4 FEATURE 4: PATIENT CARE EXPERIENCE & FEEDBACK RATINGS REGISTRY
--------------------------------------------------------------------------------
- Purpose: Records patient satisfaction and clinical quality ratings immediately 
  following triage intake to track department service performance.
- Fire-Walling Invariant: Feedback ratings are strictly isolated from clinical 
  scoring, risk calculations, and triage priority algorithms.
- Subsystem Components:
  * Interactive 1-to-5 star selector with sanitized 1,000-character comment area 
    presented on Step 4 of intake.html.
  * Stored in MySQL 'feedbacks' table via Feedback.java.
  * Admin Telemetry Console: Located in analytics.html, displaying overall average 
    rating, total submission count, 5-star to 1-star percentage bars, and qualitative feedback.
  * Endpoints: POST /api/v1/feedback, GET /api/v1/feedback/summary.

--------------------------------------------------------------------------------
5.5 FEATURE 5: CLINICAL AI CHATBOT ASSISTANT (MEDIAI ASSISTANT)
--------------------------------------------------------------------------------
- Purpose: A persistent, floating clinical assistant widget (#mediaiChatbotLauncher) 
  mounted across all HTML pages to assist users with vital baselines and ER guidance.
- Clinical Intelligence & Safety Safeguards:
  * Red-Flag Emergency Interception: Real-time regex detection of life-threatening 
    complaints (crushing chest pain, severe breathlessness, heavy bleeding, stroke signs) 
    in both English and Tamil.
  * Emergency Directive: When triggered, sets is_emergency = true, halts routine Q&A, 
    and displays an immediate directive to dial 108 / 112 / 911 or proceed to ER bay.
  * Clinical Knowledge Engine: Explains normal physiological vital baselines, 
    fever thresholds (>= 38.5°C), and 1-10 pain intensity scales.
  * Bilingual Interchange: Instant toggle between English (EN) and Tamil (தமிழ்).
  * Hands-free Voice Input: Microphone button inside chat drawer for voice queries.
  * Persistent History: Messages stored in MySQL 'chat_messages' table.

6. RELATIONAL DATABASE ARCHITECTURE & HIBERNATE ENTITY SCHEMAS
================================================================================
All relational database tables are managed in MySQL 8.0 using Hibernate ORM with 
spring.jpa.hibernate.ddl-auto=update:

1. TABLE: patients (Entity: Patient.java)
   - id: VARCHAR(36) PRIMARY KEY
   - mrn_hash: VARCHAR(64) NOT NULL UNIQUE (SHA-256 salted hash)
   - encrypted_name: TEXT NOT NULL (AES-256-GCM encrypted)
   - dob: DATE NOT NULL
   - gender: VARCHAR(10) NOT NULL
   - blood_group: VARCHAR(5)
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

2. TABLE: vital_signs (Entity: VitalSigns.java)
   - id: VARCHAR(36) PRIMARY KEY
   - patient_id: VARCHAR(36) NOT NULL, FOREIGN KEY -> patients(id)
   - heart_rate: INT NOT NULL (Validation: 20 - 300 bpm)
   - systolic_bp: INT NOT NULL (Validation: 40 - 260 mmHg)
   - diastolic_bp: INT NOT NULL (Validation: 20 - 160 mmHg, DBP < SBP)
   - respiratory_rate: INT NOT NULL (Validation: 4 - 60 bpm)
   - spo2: DECIMAL(4,1) NOT NULL (Validation: 50.0 - 100.0 %)
   - temperature: DECIMAL(4,1) NOT NULL (Validation: 30.0 - 45.0 °C)
   - blood_glucose: DECIMAL(5,1) (Validation: 20.0 - 800.0 mg/dL)
   - recorded_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

3. TABLE: triage_assessments (Entity: TriageAssessment.java)
   - id: VARCHAR(36) PRIMARY KEY
   - patient_id: VARCHAR(36) NOT NULL, FOREIGN KEY -> patients(id)
   - vitals_id: VARCHAR(36) NOT NULL, FOREIGN KEY -> vital_signs(id)
   - chief_complaint: TEXT NOT NULL
   - calculated_category: VARCHAR(10) NOT NULL (CRITICAL, HIGH, MODERATE, LOW)
   - risk_score: INT NOT NULL (Range: 0 - 100)
   - confidence_score: DECIMAL(3,2) NOT NULL
   - is_red_flag: BOOLEAN DEFAULT FALSE
   - clinical_rationale: TEXT
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

4. TABLE: triage_reviews (Entity: TriageReview.java)
   - id: VARCHAR(36) PRIMARY KEY
   - assessment_id: VARCHAR(36) NOT NULL, FOREIGN KEY -> triage_assessments(id)
   - doctor_id: VARCHAR(64) NOT NULL
   - original_category: VARCHAR(10) NOT NULL
   - final_category: VARCHAR(10) NOT NULL
   - is_overridden: BOOLEAN DEFAULT FALSE
   - override_reason: TEXT (Minimum 15 characters required on Critical downgrade)
   - reviewed_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

5. TABLE: notifications (Entity: Notification.java)
   - id: VARCHAR(36) PRIMARY KEY
   - target_role: VARCHAR(20) NOT NULL (ALL, DOCTOR, NURSE)
   - title: VARCHAR(120) NOT NULL
   - message: TEXT NOT NULL
   - priority: VARCHAR(10) NOT NULL (CRITICAL, HIGH, INFO)
   - is_read: BOOLEAN DEFAULT FALSE
   - reference_id: VARCHAR(64)
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

6. TABLE: user_otps (Entity: OtpVerification.java)
   - id: VARCHAR(36) PRIMARY KEY
   - email: VARCHAR(120) NOT NULL
   - temp_token: VARCHAR(64) NOT NULL INDEX
   - otp_hash: VARCHAR(64) NOT NULL (SHA-256)
   - attempts: INT DEFAULT 0
   - expires_at: TIMESTAMP NOT NULL
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

7. TABLE: feedbacks (Entity: Feedback.java)
   - id: VARCHAR(36) PRIMARY KEY
   - rating: INT NOT NULL (Range: 1 - 5)
   - comment: VARCHAR(1000)
   - submitter_role: VARCHAR(20) NOT NULL
   - reference_id: VARCHAR(64)
   - created_at: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

8. TABLE: chat_messages (Entity: ChatMessage.java)
   - id: VARCHAR(36) PRIMARY KEY
   - conversation_id: VARCHAR(64) NOT NULL INDEX
   - sender: VARCHAR(20) NOT NULL (PATIENT, BOT)
   - message: TEXT NOT NULL
   - language: VARCHAR(10) NOT NULL (en, ta)
   - is_emergency: BOOLEAN DEFAULT FALSE
   - timestamp: TIMESTAMP DEFAULT CURRENT_TIMESTAMP

9. TABLE: audit_logs (Entity: AuditLog.java)
   - id: VARCHAR(36) PRIMARY KEY
   - action_category: VARCHAR(64) NOT NULL
   - actor_id: VARCHAR(64) NOT NULL
   - ip_address: VARCHAR(45) NOT NULL
   - timestamp: TIMESTAMP DEFAULT CURRENT_TIMESTAMP
   - details: TEXT (Zero PHI)

10. TABLE: users (Entity: User.java)
    - id: VARCHAR(36) PRIMARY KEY
    - email: VARCHAR(120) NOT NULL UNIQUE
    - password_hash: VARCHAR(120) NOT NULL (BCrypt)
    - role: VARCHAR(20) NOT NULL (DOCTOR, NURSE, ADMIN)
    - full_name: VARCHAR(100) NOT NULL

11. TABLE: medication_records (Entity: MedicationRecord.java)
    - id: VARCHAR(36) PRIMARY KEY
    - patient_id: VARCHAR(36) NOT NULL, FOREIGN KEY -> patients(id)
    - medication_name: VARCHAR(120) NOT NULL
    - dosage: VARCHAR(50) NOT NULL
    - route: VARCHAR(30)
    - frequency: VARCHAR(50)
    - status: VARCHAR(20) DEFAULT 'ACTIVE'
    - reconciliation_notes: TEXT

7. RESTFUL WEB SERVICES API CATALOG
================================================================================
Implemented using Spring Boot RESTful Web Services:

AUTHENTICATION & TWO-STEP OTP (com.mediai.controller.AuthController):
- POST /api/v1/auth/login-step1
  Validates credentials; generates 6-digit random passcode; stores SHA-256 hash; 
  returns { tempToken, maskedEmail, expiresInSeconds }.
- POST /api/v1/auth/verify-otp
  Validates OTP hash; enforces attempt limits; issues signed JWT bearer token.
- POST /api/v1/auth/resend-otp
  Issues replacement OTP subject to 60-second cooldown rate limit.

TRIAGE & PATIENT INTAKE (com.mediai.controller.TriageController):
- POST /api/v1/triage/assess
  Accepts patient demographics, symptoms, and physiological vitals; executes 
  deterministic red-flag engine; records triage assessment; triggers clinical notification.
- GET /api/v1/triage/assessments
  Returns recent triage assessments with priority and risk scores.

DOCTOR WORKSTATION (com.mediai.controller.DoctorController):
- GET /api/v1/doctor/queue
  Returns emergency patient queue sorted by Priority (P1 > P2 > P3 > P4), 
  Risk Score DESC, and Arrival Time.
- GET /api/v1/doctor/patient/{id}
  Returns complete patient clinical profile, vital signs history, and triage record.
- POST /api/v1/doctor/override
  Records attending physician confirmation or override. Strictly enforces 
  minimum 15-character clinical rationale when downgrading a Critical case.
- GET /api/v1/doctor/medications?patientId={id}
  Returns home medications for reconciliation (prescribing/dispensing excluded).
- GET /api/v1/doctor/analytics
  Returns department throughput metrics, acuity breakdown, and concordance rates.

CLINICAL NOTIFICATIONS (com.mediai.controller.NotificationController):
- GET /api/v1/notifications?role={ALL|DOCTOR|NURSE}
  Returns unread and recent clinical notifications with priority indicators.
- PUT /api/v1/notifications/read-all
  Marks all unread notifications as read.

PATIENT FEEDBACK (com.mediai.controller.FeedbackController):
- POST /api/v1/feedback
  Records patient or staff care experience rating (1 to 5 stars) and comment.
- GET /api/v1/feedback/summary
  Returns aggregate average rating, total count, and star distribution metrics.

CLINICAL CHATBOT ASSISTANT (com.mediai.controller.ChatController):
- POST /api/v1/chat/message
  Interprets clinical query, detects emergency red flags, returns AI guidance.
- GET /api/v1/chat/history?conversationId={id}
  Retrieves conversation history for the active session.
